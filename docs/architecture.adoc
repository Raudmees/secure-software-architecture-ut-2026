== 4. Containers

.Containers of the Citizen Services Portal (source: link:../diagrams/c4_containers.puml[c4_containers.puml])
image::../diagrams/c4_containers.svg[C4 container diagram of the Citizen Services Portal]

The portal holds as little business data as possible. Case content, documents, profile data and
delegations stay with the owning agencies and registries, and the portal reads them live through
the agency integration service. The portal stores only its own data: preferences, catalogue
configuration, API client registrations, documents in transit, and the audit trail.

[cols="1,3",options="header"]
|===
|Container |Responsibility

|Citizen web app, back-office web app
|Localized citizen UI. Helpdesk, administration and audit review UI with role-limited access.

|API gateway
|Single entry point for both web apps and third-party API clients: token validation, scopes, rate limiting and API versioning.

|Identity & access
|eID/OIDC login, sessions, and role and delegation-based authorization checks. Delegations are verified against the mandate registry.

|Catalogue & profile
|Service catalogue and resident preferences. Profile data is read from registries on demand.

|Case service
|Submits requests and shows live case status. It stores no case content.

|Document service, antivirus scanner
|Every upload is scanned before it is accepted, then delivered to the agency. Downloads are fetched from the agency. The temporary document store holds files only until they are scanned and delivered.

|Signing service
|Runs the eID signing flow with the external signing service.

|Message broker
|Asynchronous delivery queue to agencies, plus notification and audit event streams.

|Agency integration
|Adapters for each agency and registry, a canonical data model, data minimization, retries and mutual TLS.

|Notification service
|In-app inbox and dispatch to email, SMS and push providers.

|Audit service, audit store
|Collects audit events from all services into append-only, tamper-evident storage, and serves resident transparency and auditor queries.

|Portal DB (minimal)
|Preferences, catalogue configuration and API client registrations.

|Observability
|Monitoring, logs and tracing for the operations and security team.
|===

Reading data live keeps the portal from becoming a second copy of agency data (R13), but it makes
the portal depend on agency availability and load (R11). When an agency is unavailable, the
portal must show that clearly rather than stale data. Asynchronous submission through the
message broker lets residents submit requests even while the agency is down. Container
ownership follows link:ownership_sketch.adoc[ownership_sketch.adoc].
