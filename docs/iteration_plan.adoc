= Project iteration plan
:toc:
:toclevels: 2

Risk IDs refer to link:../risk/risk_register.adoc[risk/risk_register.adoc]. The phases follow
the RUP lifecycle and address higher-priority risks first.

== Phase 1. Inception

Agree the scope and initial architecture, and reduce the High/High and structure-defining risks that could invalidate the project direction.

[cols="1,3,3",options="header"]
|===
|Risk |Action |Artifact or evidence

|R10
|Define the initial system context, containers and one main end-to-end flow.
|Initial C4 diagrams and sequence diagram.

|R13
|Define which case data and documents are handled by the portal and which remain with agencies.
|Data ownership and system-of-record boundaries.

|R06
|Investigate the signing integration and validate its riskiest step with a PoC or mock.
|Signing sequence and technical spike.

|R09
|Select representative external systems, compare their interfaces and test the adapter approach.
|Interface comparison and adapter PoC or mock.

|R11
|Estimate users, requests and data volumes, and define the peak-load scenario.
|Capacity assumptions, target workload and response-time target (99% under 500 ms for portal-internal requests at estimated peak load).

|R12
|Define the authorization boundary and validate one delegated-access path.
|Delegation model and small authorization spike.

|R15
|Model queued delivery during an agency outage and test it with a stub agency. 
|Queued-delivery flow and outage test (Workflow and messaging).

|===

== Phase 2. Elaboration

Establish the executable architecture baseline and reduce the remaining high-impact risks.

[cols="1,3,3",options="header"]
|===
|Risk |Action |Artifact or evidence

|R01
|Model and validate one national eID authentication flow.
|Authentication sequence and PoC or mock.

|R02
|Evaluate the case-management approach with one representative workflow.
|Workflow model and technology decision.

|R04
|Prototype document upload and antivirus scanning, including failure handling.
|Document-processing PoC.

|R07
|Define audit events and trace one action across components.
|Audit-event model and example trail.

|R08
|Define security for one third-party API interaction.
|API authentication, authorization and audit model.

|R10
|Connect the main components into an executable architecture baseline.
|Representative vertical slice.

|R14
|Confirm fallback requirements for residents without eID and model one valid path.
|Fallback authentication or service-path model.
|===

The executable architecture will implement these use cases:

. A resident logs in with eID and views their own cases.
. A resident submits a request with a document to one agency.
. A delegate opens a case of the person they represent.
. The portal detects a status change at an agency and the resident is notified.
. A helpdesk worker opens a document and an audit record is written.


== Phase 3. Construction

Build the system on the validated architecture and integrate the selected mechanisms.

[cols="1,3,3",options="header"]
|===
|Risk |Action |Artifact or evidence

|R02
|Implement the representative workflow in the selected case-management approach.
|The workflow runs from submission to agency decision with status updates visible to the resident.

|R03
|Implement the notification abstraction with at least two channels.
|A notification is delivered via two channels, when one provider fails, it is retried and not lost.

|R04
|Implement the upload and antivirus-scanning flow.
|An infected test file is rejected. During a scanner outage, uploads stay quarantined and are never served.

|R05
|Implement representative document-retention rules.
|Response measures of QA scenario 3 pass (delivered documents deleted within 10 min, none older than 7 days).


|R06
|Implement the signing flow against the signing test environment.
|A document is signed and its signature validates, a modified document fails validation.


|R07
|Apply the audit-event model to all features that access citizen data.
|Response measures of QA scenario 2 pass (every access audited within 5 s, no document content in records).

|R08
|Apply the third-party API security model to the public API.
|Authorization test: clients cannot access operations or data outside their granted scopes.

|R09
|Add the adapters for the selected external systems.
|Response measures of QA scenario 5 pass (no changes to core or existing adapters).

|R10
|Complete the main end-to-end citizen-service flow.
|Integrated vertical slice.

|R12
|Apply the authorization and delegation model to all endpoints exposing citizen data.
|Response measures of QA scenario 1 pass, and all requests for another resident's data without authorization are denied.

|R16
|Define the public API versioning and deprecation policy and add contract tests for the public API and one agency adapter.
|Published versioning policy; contract tests pass against the current API version and one agency test environment.

|===

== Phase 4. Transition

Validate the completed system under realistic load and failure conditions, and prepare it for operation.

[cols="1,3,3",options="header"]
|===
|Risk |Action |Artifact or evidence

|R11
|Run load tests using the capacity estimates and peak-load scenario from Inception.
|Load-test results showing the Phase 1 response-time target is met at estimated peak load, and identified bottlenecks.

|R03, R04, R09
|Test notification-provider, antivirus-service and agency-system failures and recovery.
|Failure and recovery test results.

|R07, R10
|Validate observability and the end-to-end flow in the deployment environment.
|Operational and end-to-end validation results.

|R15
|Make one agency system unavailable during the end-to-end flow and check that requests are queued and delivered after recovery.
|Response measures of QA scenario 4 pass (0 lost or duplicated requests, delivered within 15 min of recovery).
|===
