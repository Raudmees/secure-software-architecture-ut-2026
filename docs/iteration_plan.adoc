== Phase 1. Baseline Architecture (Inception)

Establish the initial system structure, service boundaries, workflows and common interface conventions before committing to more detailed architectural decisions.

[cols="1,3,3",options="header"]
|===
|Risk |Action |Artifact or evidence

|R10
|Define the initial containers/services and their interfaces, then model one representative end-to-end flow across them.
|Baseline container diagram and end-to-end sequence diagram showing how the main components interact.

|R02
|Model one representative case-management workflow and evaluate whether an existing workflow/case-management solution can support it.
|Case-management workflow model and a short technology evaluation / decision record.

|R11
|Do research to estimate the maximum expected users, requests and data volumes using public statistics.

Build an initial infrastructure MVP and test it with a load test.
|Capacity estimates and infrastructure scalability parameters.

Load-test results for the infrastructure with those parameters, at a level acceptable for a good-quality application (99.9th percentile response time under 300 ms).
|===

== Phase 2. Security, Privacy and Auditability (Elaboration)

Validate that the architecture can support the required identity, signing, document-security, retention, authorization and auditability properties.

[cols="1,3,3",options="header"]
|===
|Risk |Action |Artifact or evidence

|R01
|Investigate one national eID integration approach and model the authentication flow, trust relationships, certificates and test-environment requirements.
|eID authentication flow / sequence diagram and a small PoC or mock integration.

|R04
|Prototype the document upload and antivirus-scanning flow, including successful scanning, infected files and scanner failure.
|Document-processing flow and antivirus integration PoC.

|R05
|Define representative retention rules and check whether the selected storage approach can enforce them automatically.
|Document-retention design describing automated retention or the application-level fallback.

|R06
|Investigate available eID signing APIs/test environments and validate the most difficult part of the signing flow.
|Digital-signing sequence diagram and technical spike / PoC.

|R07
|Define the required audit events and verify that one user action can be correlated across multiple components.
|Audit-event model and an example end-to-end audit trail.

|R08
|Define authentication, authorization/scopes and auditing for one representative third-party API interaction.
|Third-party API security model and API authentication/authorization flow.

|R12
|Decide what the portal enforces itself versus what it delegates to the identity provider or the owning agency.
|One delegated-access case modelled end to end.
|===

== Phase 3. External Integrations and Interfaces (Construction)

Validate that external organizations and third-party systems can be integrated without forcing major changes to the internal architecture.

[cols="1,3,3",options="header"]
|===
|Risk |Action |Artifact or evidence

|R09
|Compare representative interfaces from at least two external systems and map their identifiers and data formats into the internal model.
|External integration mapping and adapter/canonical data model design.

|R01, R06, R08
|Treat eID, digital signing and third-party API access as external dependencies and document the interfaces between the system and those external services.
|External interface contracts for identity, signing and third-party API access.

|R10
|Connect representative components and external-system mocks into one vertical flow.
|Integrated vertical-slice prototype using real interfaces where possible and mocks where necessary.
|===

== Phase 4. Availability, Operations and Evolution (Transition)

Validate that the architecture behaves predictably when dependencies fail and that components and interfaces can evolve without requiring system-wide redesign.

[cols="1,3,3",options="header"]
|===
|Risk |Action |Artifact or evidence

|R03
|Define a common notification abstraction and test at least two channels, including retry and provider-failure behaviour.
|Notification interface/design and failure/retry handling model.

|R04
|Define what happens when the antivirus service is slow or unavailable.
|Document-processing failure-handling design.

|R09
|Validate that an external-interface change can be handled mainly inside its adapter instead of changing unrelated services.
|Updated integration contract / compatibility example demonstrating interface isolation.

|R10
|Run the representative end-to-end flow with selected component or external-service failures and check that failures remain contained.
|End-to-end architecture validation results and an updated architecture diagram if changes are required.

|R11
|Validate the Phase 1 capacity estimates against the refined architecture, focusing on shared components every request passes through, using load tests.
|Capacity calculation or load-test results for the peak load scenario, showing whether the identified bottlenecks meet the target.
|===
