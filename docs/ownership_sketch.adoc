= Ownership Sketch
:toc:

Initial ownership assumptions for the containers in
link:architecture.adoc[architecture.adoc] (section 4). Teams follow the Team Topologies
types.

== Ownership

[cols="2,1,3",options="header"]
|===
|Team |Type |Containers owned

|Portal Services Team
|Stream-aligned
|Citizen web app, back-office web app, Portal backend (catalogue and preferences, cases,
documents, signing workflow, notifications)

|Identity and Access Team
|Complicated-subsystem
|Identity & access

|Agency Integration Team
|Stream-aligned
|Agency integration, API gateway (public and provider APIs, versioning)

|Audit and Transparency Team
|Complicated-subsystem
|Audit service, audit store

|Platform and Operations Team
|Platform
|Message broker, Portal DB (minimal), Temporary file store, antivirus scanner, observability
|===

The Platform and Operations Team runs the shared stores and the broker.

== Conway check

Where teams must coordinate, and what keeps that coordination small.

[cols="2,3,3",options="header"]
|===
|Teams |Why they coordinate |Reduced by

|Portal Services ↔ Identity and Access
|Every protected operation needs an authorization decision
|Identity and Access offers one fixed way to ask "may this user do this?", and changes it only with a new version

|Portal Services ↔ Agency Integration
|Requests and documents go to agencies. New backend endpoints need API gateway changes
|Agency data is translated into one common internal format, so the backend never sees agency-specific formats. Portal Services adds its own gateway routes; Agency Integration only reviews changes to the public API

|All teams ↔ Audit and Transparency
|Every container emits audit events
|The audit team publishes one audit event format and a ready-made library for sending events

|All teams ↔ Platform and Operations
|All teams use the message broker and databases that the Platform team runs
|Teams create their own queues and databases with ready-made templates, so they do not wait for the Platform team
|===
