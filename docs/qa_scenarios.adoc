== Scenario 1. Delegation registry unavailable

[cols="1,3",options="header"]
|===
|Field |Content

|*Scenario name*
|Deny delegated access when the delegation cannot be verified.

|*Business goal*
|*BG-2* - process citizen data securely.

|*Relevant quality attributes*
|Authorization and confidentiality (*QA-1*), availability and resilience (*QA-3*).

|*Stimulus*
|A resident requests access to another person's case as their delegate.

|*Stimulus source*
|An authenticated resident.

|*Environment*
|The delegation registry is unavailable.

|*Artifact*
|The portal's authorization and delegation checks.

|*Response*
|Deny the delegated request and return a clear temporary-unavailability message. The resident's access to their own cases continues normally.

|*Response measure*
|All requests in the unavailable-registry test set are denied, no case data is returned, and each response is returned within 3 seconds. Access to the resident's own cases stays available during the outage.

|*Questions*
|May valid delegation decisions be cached, and for how long?

|*Issues*
|Emergency or legally urgent access requires a separate scenario.
|===

== Scenario 2. Authorized document access is recorded

[cols="1,3",options="header"]
|===
|Field |Content

|*Scenario name*
|Record a helpdesk worker's access to a citizen document.

|*Business goal*
|*BG-3* - make personal-data access verifiable.

|*Relevant quality attributes*
|Privacy and data minimization (*QA-2*), auditability and accountability (*QA-4*).

|*Stimulus*
|An authorized portal helpdesk worker opens a document attached to a citizen's case through the Back-office web app.

|*Stimulus source*
|An authenticated portal helpdesk worker.

|*Environment*
|Normal operation.

|*Artifact*
|The document access interface and audit logging.

|*Response*
|Allow the access and record the actor, organization or role, time, document ID, action and outcome without recording document content.

|*Response measure*
|Every access in the test set has a complete audit record available within 5 seconds, and no document content is present in the record.

|*Questions*
|Who may read these records, and how long are they retained?

|*Issues*
|Presenting audit history to residents is outside this scenario.
|===

== Scenario 3. Delivered documents are removed from the portal

[cols="1,3",options="header"]
|===
|Field |Content

|*Scenario name*
|Delete the portal's copy of a document once the agency has received it.

|*Business goal*
|*BG-2* - process citizen data lawfully and only for appropriate purposes.

|*Relevant quality attributes*
|Privacy and data minimization (*QA-2*), regulatory compliance (*QA-13*).

|*Stimulus*
|The receiving agency confirms that it has received a document submitted by a resident.

|*Stimulus source*
|An agency back-end e-service.

|*Environment*
|Normal operation. The Temporary doc store also holds documents that have not been delivered yet.

|*Artifact*
|The Temporary doc store and its deletion rules.

|*Response*
|Delete the document from the Temporary doc store and record the deletion without recording document content. Documents that are never delivered are deleted when the maximum transit time ends.

|*Response measure*
|Every confirmed document in the test set is deleted within 10 minutes of the confirmation and has an audit record of the deletion. A daily check finds zero documents older than 7 days in the store.

|*Questions*
|Is 7 days an acceptable maximum transit time, and what happens to a queued request whose documents are deleted before delivery (see Scenario 4)?

|*Issues*
|Copies of documents in backups are outside this scenario.
|===

== Scenario 4. Agency unavailable during submission

[cols="1,3",options="header"]
|===
|Field |Content

|*Scenario name*
|Preserve a submitted request while its agency is unavailable.

|*Business goal*
|*BG-5* - maintain essential capabilities during external failures.

|*Relevant quality attributes*
|Availability and resilience (*QA-3*), recoverability and data durability (*QA-8*).

|*Stimulus*
|A resident submits a request while the receiving agency system is unavailable.

|*Stimulus source*
|An authenticated resident.

|*Environment*
|The portal is operating, but the receiving agency is not responding.

|*Artifact*
|The request-submission service and agency-delivery queue.

|*Response*
|Store the request once, mark it as awaiting delivery, and confirm receipt to the resident.

|*Response measure*
|Every request in the outage test set is confirmed within 3 seconds and is delivered exactly once within 15 minutes after the agency recovers.

|*Questions*
|Which timestamp is the official submission time, and how long may a request remain queued?

|*Issues*
|Services requiring synchronous agency validation need a separate scenario.
|===

== Scenario 5. Add a service through an agency API

[cols="1,3",options="header"]
|===
|Field |Content

|*Scenario name*
|Add one agency service without changing the portal core.

|*Business goal*
|*BG-4* - onboard agencies without major changes.

|*Relevant quality attribute*
|Evolvability and interoperability (*QA-5*).

|*Stimulus*
|An agency requests integration of one service through its documented REST API.

|*Stimulus source*
|The agency service owner.

|*Environment*
|Development time, with existing integrations already supported.

|*Artifact*
|The agency adapter and service catalogue.

|*Response*
|Add an adapter and service configuration without changing the portal core or existing adapters.

|*Response measure*
|The integration takes no more than 10 person-days, requires zero changes to the core or existing adapters, and passes the existing integration tests.

|*Questions*
|Is the 10 person-day target realistic for the first integrations?

|*Issues*
|Non-REST or undocumented agency interfaces require separate scenarios.
|===
