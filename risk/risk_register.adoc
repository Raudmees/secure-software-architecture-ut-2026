== Project risks

Risks to completing the project itself: gaps in team knowledge, unvalidated technology choices and integration unknowns.

[cols="1,5,1,1,1,5",options="header"]
|===
|ID |Project risk |Likelihood |Impact |Priority |Treatment

|R01
|The team has no prior experience with national eID integration and may underestimate the required protocols, certificates, trust relationships or test setup, preventing completion of a credible eID integration design.
|Medium
|High
|Medium
|Investigate one national eID integration path immediately; document the authentication flow and build/validate a minimal PoC or mock integration.

|R02
|A suitable existing workflow/case-management solution may not satisfy the project's workflow, security or integration requirements, leaving insufficient time to design an alternative.
|Medium
|High
|Medium
|Evaluate 2-3 realistic options early against a small set of required workflows; create a minimal workflow PoC and define a fallback custom solution.

|R03
|Email, SMS, push and in-app notifications may require substantially different delivery mechanisms, making a single notification architecture more complex than expected and delaying completion of the capability.
|Medium
|Medium
|Low
|Prototype the common notification interface and implement/mock at least two different channels to validate the abstraction.

|R04
|The selected antivirus scanning solution may not integrate cleanly with the planned upload/storage flow, requiring changes to file storage, quarantine or asynchronous processing.
|Medium
|High
|Medium
|Test a representative upload -> scan -> accept/reject flow early, including a deliberately infected test file and scanner failure.

|R05
|The chosen storage approach may not support the required automated retention rules cleanly, requiring custom deletion/lifecycle logic and redesign of document metadata.
|Medium
|Low
|Low
|Define representative retention rules and validate whether the selected storage technology can enforce them automatically; identify fallback application-level lifecycle processing.

|R06
|The team has no prior eID digital-signing experience and may be unable to validate the complete signing workflow or obtain a usable test environment, leaving a core capability architecturally unresolved.
|High
|High
|High
|Treat signing as an early technical spike: determine available signing APIs/test environments, model the full signing sequence and validate the riskiest integration step.

|R07
|The team may choose a normal application-logging approach that cannot provide the required correlation, integrity and traceability for audit events, causing late architectural changes across multiple services.
|Medium
|High
|Medium
|Define required audit events and properties first; prototype logging one end-to-end user action across components and verify that it can be reconstructed reliably.

|R08
|The team may not sufficiently understand the security and regulatory constraints applying to third-party API access, causing the initial API authentication/authorization design to be unusable and requiring redesign.
|Medium
|High
|Medium
|Identify the concrete requirements early and design one representative third-party API interaction including authentication, authorization/scopes, auditing and error handling.

|R09
|Registry systems may not be compatible with the portal (different IDs, data formats or interfaces), and agencies may implement the agency API late or incorrectly, so each integration may take much longer than planned and we may not finish all 2-3 required integrations.
|High
|High
|High
|Compare the interfaces of the selected registries and define a common internal data model with one adapter per registry. Publish the agency API early with conformance tests and a stub agency, and validate it with at least two agencies.

|R10
|Components may appear workable independently but fail when combined into an end-to-end citizen-service flow, revealing incompatible assumptions late in the project.
|Medium
|High
|Medium
|Create an early vertical slice such as login -> submit request -> attach document -> status update -> notification -> audit event, using mocks for unfinished components.

|R11
|The team has no experience designing systems at national scale, so we lack a reliable basis for estimating load, data volumes and peak demand. If scaling and storage decisions are made on guesswork, then the chosen architecture may fail to handle realistic workloads, and the bottlenecks will only be discovered late, requiring structural redesign.
|High
|High
|High
|Estimate expected users, requests and data volumes using public statistics. Identify peak load scenarios.

|R12
|The container design makes Identity & access responsible for every authorization decision (SG-2), but the authorization model itself is not yet defined: roles, delegation scopes, and how the portal checks who may access cases and documents that the agencies hold. If it stays undefined, then each container that exposes citizen data will implement its own checks, and access rules will be inconsistent or missing.
|High
|High
|High
|Define the authorization model in Identity & access (roles, delegation scopes, and how case and document ownership is checked against the owning agency) and model one delegated-access case end to end (for example a representative acting on behalf of another person).

|R13
|It is unclear whether the portal or agencies should store and process case data and documents. A wrong boundary could require major architectural redesign.
|Medium
|High
|Medium
|Define data ownership and system-of-record boundaries for one representative service. Write a decision in ADR-0002. Decided in link:../adrs/ADR-0002-portal-stores-minimal-data.adoc[ADR-0002].

|R14
|It is unclear whether residents without eID require a legally valid fallback authentication method. If required, they should not be able to do everything that eID-authenticated users can. That means we must distinguish between users based on how they authenticated. If this is not designed, the portal will either block legitimate users from services they are entitled to or allow sensitive actions for users with weaker authentication.
|Medium
|High
|Medium
|Confirm the requirements and model one fallback path. Define which operations require national-eID-level authentication, and carry the login method in the session so authorization can check it.

|R15
|Because the portal reads agency data live (ADR-0002), an unavailable or slow agency system means requests cannot be delivered and live case status cannot be shown for that agency's services. 
|High
|High
|High
|Queue requests in the message broker during outages, timeouts and circuit breakers in the agency integration service, and show residents a clear pending status (QA scenario 4). 

|R16
|If the portal's public API or agency API changes without a versioning and deprecation policy, then third-party clients or agency integrations break.
|Medium
|High
|Medium
|Version the public API with a published deprecation period; isolate each agency behind its own adapter; run contract tests against agency test environments.

|R17
|Agency references collide. A reference is unique only inside one agency. If the portal looks a case up by reference alone, two agencies using for example CASE-123 point to the same record and a resident sees the wrong case.
|Medium
|High
|Medium
|Key the mapping by agency and reference together; test with the same reference from two stub agencies.

|R18
|If Identity & access caches delegation decisions (open question in link:../docs/qa_scenarios.adoc[QA scenario 1]), then a delegate whose mandate was revoked in the registry can keep submitting requests for the citizen until the cache expires.
|Medium
|High
|Medium
|Check the mandate against External registries on every protected action, or cache for at most 5 minutes. Test: revoke the mandate in a stub registry, retry the submission, and expect a 403 and an audit event naming both people.

|R19
|If the portal accepts a signature that the signing service returns after the resident cancelled the session in the portal (`cancelSigning`), then a document the resident decided not to sign is delivered to the agency as signed.
|Medium
|High
|Medium
|Cancelling and completing both change the session from awaiting confirmation in one conditional update in Portal DB, so only one succeeds; a signature for a cancelled session is discarded and audited. Test: start signing against a stub signing service, cancel, then let the stub return a valid signature; expect `410 SIGNING_ENDED` from `completeSigning` and nothing queued for the agency.

|R20
|If `cancelSigning` does not check that the caller started the session, then anyone who obtains a session ID can cancel other residents' signing and learn that the session exists.
|Low
|Medium
|Low
|Return `404` unless the signed-in user started the session; rate-limit the operation and audit every cancellation. Test: call `cancelSigning` with another resident's token; expect `404` and the session still awaiting confirmation.

|R21
|If the resident confirms the prompt on the phone after cancelling in the portal (step 3 of "Late signature after a cancellation" in link:../docs/architecture.adoc[architecture.adoc]), then the phone shows the prompt as confirmed while the portal has discarded the signature. The resident may believe the document is signed and not sign again, so the agency never receives a signature.
|Medium
|Medium
|Low
|The portal decides the cancellation alone and keeps showing "Signing cancelled" and that the document is not signed, whatever the phone shows. `completeSigning` returns `410 SIGNING_ENDED`, which tells the client to reload the document; the document still awaits a signature and a new attempt can start at once (link:../adrs/ADR-0004-cancel-signing-as-new-endpoint.adoc[ADR-0004]). The portal also asks the signing service to withdraw the prompt, but does not rely on it. Test: start signing against a stub signing service, cancel, let the stub confirm the prompt, call `completeSigning` and reload the document; expect `410 SIGNING_ENDED`, the document shown as not signed and still awaiting a signature, and a new `startSigning` with a new key returning `202`.

|R22
|If `cancelSigning` and `completeSigning` reach the portal at almost the same moment (the race at step 3 of the same timeline) and both are accepted, then the resident is told "Signing cancelled" while the signed document is delivered to the agency.
|Low
|High
|Low
|Both operations change the session from `AWAITING_CONFIRMATION` in one conditional update in Portal DB, so only the first one succeeds and the other gets `410 SIGNING_ENDED`. If completing wins, the portal shows "signed" and the document is delivered once. Test: with a stub signing service that already holds a valid signature, send `cancelSigning` and `completeSigning` at the same time for 100 sessions. Expect each session to end in exactly one of two ways: cancelled, with no signed document in the Temporary file store, nothing in the Message broker and nothing received by a stub agency; or completed, with `cancelSigning` returning `410` and the stub agency receiving the document once. In both cases the document page shows the same result as the session in Portal DB.
|===
